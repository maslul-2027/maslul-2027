## 2. זהות והרשאות (דורש אישור הבעלים — לא הוענק על ידי)
1. **הגדרה ראשונה:** אסימון `BOOTSTRAP_TOKEN` חד-פעמי (סוד ב-Cloudflare) → מנהל ראשון → בחירת **PIN אישי בן 4 ספרות** (בלי TOTP ובלי קוד באימייל — החלטת הבעלים 25.11.2026, **פיילוט סינתטי בלבד; לא מאושר לנתוני אמת**). אם ההגדרה הראשונה נקטעה: טאב "הגדרה ראשונית" + אותו אסימון התקנה מנפיק קישור חדש לאותו חשבון (בלי מחיקה ובלי חשבון חדש).
2. **בקשת גישה:** משתמש שולח שם+אימייל → המנהל מאשר במסך "הרשאות" ובוחר תפקיד/צוות/מחלקה → נוצר **קישור הצטרפות חד-פעמי** שהמנהל מעביר בעצמו.
3. **כניסה:** אימייל + **PIN בן 4 ספרות** (נבחר פעם אחת בהרשמה; נשמר רק כ-HMAC עם `APP_SECRET`, סוד שאינו במסד — אין ניחוש אופליין; PIN קל כמו 0000/1234 נדחה) ; הגנות שרת חלופיות: ניחוש אונליין נחסם בנעילת חשבון מדורגת (5 ניסיונות) ובהגבלת קצב ל-IP (הסוד מוצפן AES-GCM, צעד משומש נדחה).
4. סשן: עוגיית `__Host-` HttpOnly Secure SameSite=Strict, CSRF לכל סשן + בדיקת Origin מדויקת, פקיעת סרק 60 דק׳ / מוחלטת 12 ש׳, נעילת חשבון + הגבלת קצב לפי IP, **ביטול מיידי** (הבקשה הבאה נכשלת).
5. **האימייל הוא מזהה שהמנהל מאשר — לא הוכחת בעלות על תיבת דואר** (אין שליחת מייל במסלול חינמי, וגם אין SMS). זו החלטה שדורשת אישור הבעלים/אבטחת מידע לפני שימוש מבצעי.
6. `workers.dev` ציבורי: הקליפה ציבורית אך **אין בה נתונים**; כל נתיב נתונים דורש סשן. אפשרות מומלצת בהמשך (חינמית): Cloudflare Access מעל הדומיין.

## 6. חיבור Cloudflare Free — GitHub Actions + Wrangler (ללא אפליקציית GitHub של Cloudflare)
**למה:** בחירת המאגר באינטגרציית Cloudflare נתקעת על חשבון אחר (שינוי user-scoped picker מ-10.11.2026). המסלול הזה לא משתמש באינטגרציה: GitHub מריץ `wrangler` עם אסימון שהבעלים יוצר. **הכול בלחיצות בדפדפן — בלי קוד, בלי טרמינל, בלי תשלום.**
**תיקון תיעוד:** המאגר `maslul-2027/maslul-2027` **ציבורי** (`private:false`, נבדק מול GitHub API) — קודם נכתב בטעות "פרטי". משמעות: הקוד גלוי לכולם, ולכן **רק נתונים סינתטיים**; הסודות לעולם לא במאגר. כפתור Deploy to Cloudflare אפשרי טכנית (מאגר ציבורי) אך לא נבחר — מסלול ה-Actions מבוקר יותר. לא משנים visibility ללא הוראה מפורשת.

### מה נבנה (קוד בלבד, לא הופעל)
- `.github/workflows/cloudflare-deploy-test.yml`. job `verify` רץ בכל push לענף `cloudflare/free-shared-test` — בנייה, בדיקות סטטיות ו-`wrangler deploy --dry-run`, **בלי סודות**. job `deploy` רץ **רק אם** כל השלושה: (1) משתנה מאגר `CF_DEPLOY_ENABLED=yes`, (2) Environment `cloudflare-test` עם הבעלים כמאשר חובה (לחיצת Approve), (3) שני סודות ה-Cloudflare קיימים **רק** כסודות של אותו Environment. פעולות צד-שלישי: אין (רק `actions/*`). `main`/Pages: לא נוגעים.
- `scripts/cf_ci_deploy_prepare.js`: מוצא את D1 `maslul-test-db` או יוצר אותו (Free), ומזריק את המזהה לקובץ פריסה זמני בלבד — לא מסתמכים על הקצאה אוטומטית (בטא).
- `APP_SECRET` ו-`BOOTSTRAP_TOKEN` **אינם** סודות GitHub: נשמרים רק ב-Cloudflare כ-Worker Secrets (פריסות לא מוחקות אותם).
- - **פריסה ראשונה בשלבים (תוקן אחרי הערת המנהל):** ה-Worker בלי סודות אפליקציה **לא קורס ולא "מוכן"**: `GET /auth/status` עונה `{configured:false, missing:[…]}` (שמות בלבד), ו-`/api`, `/auth/login`, `/auth/bootstrap` נסגרים ב-503. `scripts/cf_ci_smoke.js` מדפיס בשלב 1 `NOT READY` (+ אזהרה וסיכום ריצה "DEPLOYED BUT NOT READY") ויוצא 0 — פריסה ראשונה **אינה מוצגת כגמורה**. אחרי הוספת הסודות ב-Cloudflare מריצים שוב (Re-run all jobs) ומקבלים שלב 2: `READY=true` (בקשת נתונים בלי התחברות = 401, כותרות אבטחה). פתוח ללא הגנה → הבדיקה נכשלת. נבדק: S22 ב-`tests/cf_worker.js` (בלי סודות / סוד אחד חסר / מלא / שרת פתוח מדומה).
- **Environment ואישור עצמי:** לפי תיעוד GitHub, כשמופעל **Prevent self-review** — מי שיזם את הריצה (ה-push) **לא יכול לאשר** אותה גם אם הוא Reviewer. לכן בחשבון בודד **חובה להשאיר Prevent self-review כבוי** (או Reviewer נוסף). חשבון Free + מאגר ציבורי תומכים ב-Environments, סודות וחוקי הגנה לפי התיעוד; המאגר שייך למשתמש (לא ארגון) ופרטי=false (נבדק). **לא נבדק בפועל** (אין לי גישת API ליצירת Environment): התנהגות האישור-העצמי בחשבון הבעלים — זה שלב אימות ראשון בטלפון (§GO).
- **מגבלת GitHub:** כפתור "Run workflow" מופיע רק לקובצי workflow ב-default branch; כאן הקובץ בענף בלבד (אסור למזג ל-main). הנתיב: **ריצת ה-push** → Actions → "Cloudflare TEST deploy" → ההרצה האחרונה בענף → job `deploy` ממתין → **Review deployments → cloudflare-test → Approve and deploy**. אחרי שינוי משתנה/סוד: **Re-run all jobs** (המשתנה נקרא מחדש בתחילת ה-job). ריצת `verify` על ה-push אומתה ב-CI (ראו PR); הלחיצות של Approve/Re-run עצמן NOT_RUN עד לחשבון אמיתי. `gh workflow run --ref` עובד רק אחרי שהקובץ רץ פעם בענף.

## 6א. שחזור והתאוששות (Time Travel החינמי של D1)
| יכולת | מצב |
|---|---|
| **שחזור נקודתי עד 7 ימים אחורה** (לכל דקה), ברירת מחדל, ללא עלות, ללא R2 | קיים ב-Cloudflare לבסיסי נתונים בתשתית production; **NOT_RUN** עד שיש מסד אמיתי. מגבלה: 10 שחזורים ל-10 דקות. אינו נספר באחסון. |
| שחזור/גיבוי **מתוך האפליקציה** (כפתור) | **אין ואין בכוונה** — `backup.*` מחזיר 501 `NOT_CONNECTED`; שחזור הרסני לא יופעל אוטומטית ולא מאף משתמש/מנהל אפליקציה. |
| התאוששות מאסון **מחוץ לספק** | **אין** (Time Travel חי באותו חשבון Cloudflare). חלופה אופציונלית ללא עלות: ייצוא SQL ידני על ידי המפעיל (`wrangler d1 export` / לוח הבקרה) לקובץ מקומי מוצפן — לאחסון ארוך מ-7 ימים. נתוני פיילוט סינתטיים בלבד, לכן לא נבנה תהליך אוטומטי. |

**Runbook (מפעיל בלבד = בעל חשבון Cloudflare; לא תפקיד באפליקציה):**
1. להקפיא: לבקש מהמשתמשים להפסיק לעבוד (אפשר גם להשבית זמנית את ה-Worker מלוח הבקרה).
2. `wrangler d1 time-travel info DB` (או לוח הבקרה) — לרשום את ה-bookmark **הנוכחי** (זה כפתור ה-Undo).
3. לבחור דקה יעד (`--timestamp`) שקדמה לתקלה. **שחזור כותב על המסד החי** ומחזיר את כל הטבלאות — כולל משתמשים וסשנים.
4. `wrangler d1 time-travel restore DB --timestamp=...` (הכלי מציג bookmark קודם — לשמור).
5. **מיד אחרי:** להריץ `ops/post_restore.sql` (מבטל **את כל הסשנים**, מנקה מטמון ומגבלות קצב, רושם ביקורת). בלי השלב הזה סשן שבוטל אחרי נקודת היעד היה "חוזר לחיים". נבדק ב-S21 (סימולציה על ה-shim — לא על Cloudflare).
6. מנהל האפליקציה בודק מחדש את רשימת המשתמשים: משתמש שהוסר אחרי נקודת היעד עלול להיות פעיל שוב — להשבית ידנית. נתונים שנכתבו אחרי נקודת היעד **אבדו** (אין שחזור חלקי).
7. אם התברר שנבחרה נקודה שגויה — לחזור ל-bookmark משלב 2.
